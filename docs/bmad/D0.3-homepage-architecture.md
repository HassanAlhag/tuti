# D0.3 — Tuti Customer Homepage Architecture
## Section Architecture · Customer Web · v1.0

> This document defines the canonical section architecture for the Tuti customer
> homepage. Its purpose is to prevent ad-hoc redesigns by giving every future change
> a defined scope, owner, audit path, and expansion contract.
>
> No homepage section may be redesigned, added, or removed without first being defined
> here or updating this document. Every section must be independently auditable in D0.2.

---

## How to Use This Document

1. Before implementing any homepage change, locate the section here.
2. If the section is not defined, add it here before writing any code.
3. Implement one section at a time. Do not span section boundaries in a single change.
4. After implementation, open D0.2 and create an audit entry for the section.
5. Do not ship a section without a D0.2 audit record at `conditional` or `pass`.

---

## Homepage Purpose

Tuti is a premium UAE-based gifting marketplace. The homepage has one job:

> **Convert a visitor into someone who starts building or browsing a gift.**

The homepage does not sell a specific product. It sells the idea that Tuti is the right
place to compose a thoughtful, premium gift — combining perfume, cake/dessert, and a
personal message, sourced from curated local boutiques and delivered reliably.

### Market position

- Luxury gifting platform, not a discount aggregator
- UAE-first: local sellers, local delivery, COD-friendly
- Three product categories: **perfume · cakes & desserts · gift boxes**
- Core differentiator: the Build Your Box experience (compose a scent + sweet + message
  into one unified gift delivery)

### Future expansion areas

The architecture must accommodate these without requiring structural homepage rewrites:

| Area | Current status | Architecture readiness required |
|---|---|---|
| Occasions (birthday, Eid, anniversary, etc.) | Partial | Section 6 reserved |
| Corporate gifting | Future | Section 6 expandable |
| Seasonal campaigns (Ramadan, Valentine's, etc.) | Future | Hero + Section 6 expandable |
| Subscriptions | Future | Section 9 or standalone banner |
| Editorial / journal content | Future | Section 7 reserved |
| International sellers | Future | Section 5 expandable |

## Section Architecture

The homepage renders sections in this fixed order. Order may not change without updating
this document and re-auditing affected sections.

### Section 1 — Hero / Media Slider

**Component owner:** `apps/web/src/features/immersive/ImmersiveStory.jsx`
**CSS owner:** `apps/web/src/features/immersive/immersive.css`
**Design reference:** D1.1X (Apple-like media hero, approved 2026-06-19)
**Current audit status:** `needs-re-audit` (D1.1X implemented, not yet audited)

#### Section job

First impression and brand story. The hero establishes Tuti as a premium gifting
experience before any product is shown. It must signal luxury without being cold,
warmth without being generic, and UAE cultural fit without being cliché.

#### User question it answers

> "Is this the right kind of place for me to buy a gift?"

#### Primary CTA

**Build Your Gift** — calls `goToBuildBox`. Present on the final chapter of the hero
story (Chapter 4: Gift it beautifully).

#### Secondary CTA

**Build your gift →** — subtle editorial invite on Chapter 1. Whisper register, not
a conversion mechanic.

#### Data dependency

Static. No API calls. Chapter data lives in `apps/web/src/data/homeStoryChapters.js`.
Images are local assets. No loading state, no error state, no skeleton.

#### Future expansion points

- Additional chapters can be added to `homeStoryChapters.js` without CSS changes
- Seasonal chapter swap: replace one chapter image/copy for Ramadan, Valentine's, etc.
  without any architectural change
- Video chapter: replace `<img>` with `<video autoPlay muted loop playsInline>` inside
  the same image layer when video assets are available
- A/B testing: swap chapter order or copy via data, not component structure

#### Design risk

**HIGH.** The hero has been redesigned three times (D1.1 → D1.1R → D1.1X). The main
failure mode is scope creep — the hero becomes a navigation section, a product rail,
or a full homepage replacement. Hard constraint: **the hero must not contain product
data, category links, or any section from the list below.**

#### Audit priority

**Priority 1.** The hero sets the premium expectation for the entire visit. A poor hero
degrades conversion on every section below it.

### Section 2 — Path Selector

**Component owner:** `apps/web/src/features/homepage/` (to be assigned when implemented)
**CSS owner:** Section-specific scoped class prefix `path-` or CSS module
**Design reference:** D1.2 (pending)
**Current audit status:** `pending`

#### Section job

Help the user choose how they want to start browsing. Four clear entry paths. Each path
leads directly into a category or flow, not to another chooser.

#### User question it answers

> "Where do I start?"

#### Paths

| Path | Destination | Key visual |
|---|---|---|
| Perfumes | `goToShop("perfume")` | Perfume category image |
| Cakes & Desserts | `goToShop("cake")` | Cake category image |
| Gift Sets | `goToShop("gift_box")` | Gift set image |
| Build Your Box | `goToBuildBox` | Complete gift image |

#### Primary CTA

Per-card: **Explore** or the path label itself as an implicit CTA (card is a button).

#### Secondary CTA

None. The section is the CTA.

#### Data dependency

Static. Path definitions and images are hardcoded. No API calls.

#### Future expansion points

- Add a fifth path (e.g., Occasions, Subscriptions) by adding one entry to the path
  data array — no layout change if the grid is flexible (auto-fill or wrap)
- Personalised path ordering based on user history (API-driven reorder in the future)
- Highlight a seasonal path (e.g., Eid collection) with a badge or accent border

#### Design risk

**MEDIUM.** Risk of duplicating the hero or becoming a second navigation bar. Hard
constraint: **this section must not repeat the hero copy or provide free-text search.**
Each card must go directly to a category or flow — no intermediate pages.

#### Audit priority

**Priority 2.** Directly below the hero; the first point where the user makes a
navigational decision.

### Section 3 — Gift Builder Preview

**Component owner:** `apps/web/src/features/homepage/` (to be assigned)
**CSS owner:** Section-specific scoped class prefix `gift-preview-` or CSS module
**Design reference:** D1.3 (pending)
**Current audit status:** `pending`

#### Section job

Explain Tuti's unique differentiator — the Build Your Box flow — in three or four
steps. Educate users who have never seen a composed gift experience. Build desire before
showing a product.

#### User question it answers

> "How does the Build Your Box thing actually work?"

#### Steps

| Step | Label | Copy direction |
|---|---|---|
| 1 | Choose a scent | Pick a perfume from boutique sellers |
| 2 | Add something sweet | Pair with a cake or dessert |
| 3 | Personalise it | Write your message and choose packaging |
| 4 | Gift it beautifully | One box, one delivery, one complete gift |

#### Primary CTA

**Start building** — calls `goToBuildBox`.

#### Secondary CTA

Optional: **See gift sets** — calls `goToShop("gift_box")` for users who do not want
to compose from scratch.

#### Data dependency

Static. Steps are editorial copy, not API data.

#### Future expansion points

- Animated step reveal on scroll (progressive disclosure)
- Interactive preview: clicking a step shows a product thumbnail from that category
  (requires API integration — treat as a future enhancement, not a baseline requirement)
- Corporate gifting variant: swap steps for corporate flow (bulk, branding, delivery)

#### Design risk

**LOW-MEDIUM.** Risk of becoming too tutorial-heavy and slowing down decisive buyers.
Hard constraint: **this section must be skimmable in under five seconds.** Step labels
must be short. Body copy must be optional (collapsed or visually secondary).

#### Audit priority

**Priority 3.** Key conversion education section; directly supports Build Your Box
revenue.

### Section 4 — Featured Product Rails

**Component owner:** `apps/web/src/features/homepage/AdaptiveProductEdit.jsx`
**CSS owner:** Existing `featured-product-*` class system in `storefront.css`
**Design reference:** D1.4 (pending)
**Current audit status:** `pending`

#### Section job

Quick purchase discovery. Show real products with prices. Give users a reason to click
into a product detail page or add to cart. These are the homepage's highest-intent
conversion surfaces.

#### User question it answers

> "What's actually available? Is there something I want right now?"

#### Rails

| Rail key | Label | Data source |
|---|---|---|
| `luxury_picks` | The current edit / Luxury picks | Admin merchandising API |
| `new_arrivals` | New arrivals / Fresh at Tuti | Admin merchandising API |
| `best_pairings` | Best gift pairings | Admin merchandising API (future) |
| `occasion_picks` | For the occasion | Admin merchandising API (future) |

#### Primary CTA

Per-product card: **View product** — calls `goToProduct(productId)`.

#### Secondary CTA

Per-rail heading: **View all** or **Explore** — calls `goToShop(category)` (optional;
not always required).

#### Data dependency

**HIGH.** `AdaptiveProductEdit` calls `publicMerchandisingApi.getFeaturedProducts`
per rail. If data returns empty or errors, the section renders `null` (hidden).
Loading state: handled by React Query. Skeleton: not currently implemented (future).

#### Future expansion points

- Add new rails by adding `<AdaptiveProductEdit placementKey="..." />` instances —
  no structural change required
- Skeleton loading state for each rail
- "New" badge for products within 7 days of creation
- Price range filter pill on rail heading (future)
- Personalised rail ordering based on browsing history (future)

#### Design risk

**MEDIUM.** Risk of over-railification — too many product rails making the homepage
feel like a catalogue. Hard constraint: **maximum three product rails visible at once
on the homepage without user interaction.** If more are needed, collapse behind a
"See more" control.

#### Audit priority

**Priority 4.** Highest direct revenue impact of any section below the hero.

### Section 5 — Boutique / Seller Discovery

**Component owner:** `apps/web/src/features/homepage/AdaptiveBoutique.jsx`
**CSS owner:** `boutique-*` class system in existing CSS
**Design reference:** D1.5 (pending)
**Current audit status:** `pending`

#### Section job

Build marketplace trust and introduce the concept of curated local sellers. Show that
Tuti is not a single brand but a vetted selection of independent boutiques. Support
the trust signal that feeds conversion.

#### User question it answers

> "Who is actually selling this? Can I trust these sellers?"

#### Content

| Element | Description |
|---|---|
| Featured boutiques | 2–4 seller brand cards with shop name, logo, tagline |
| Cake studios | 1–2 highlighted cake/dessert sellers |
| Seller CTA | **Visit boutique** — calls `goToSellerBrand(sellerId)` |
| Section CTA | **Explore all shops** — calls `goToShops` |

#### Primary CTA

**Visit boutique** per seller card.

#### Secondary CTA

**Explore all shops** at section level.

#### Data dependency

**HIGH.** `AdaptiveBoutique` fetches featured sellers from the API. Renders `null`
if empty. Error and loading states handled internally.

#### Future expansion points

- Seller rating / review count badge on each card
- "New seller" label for recently onboarded boutiques
- Seasonal seller spotlight (e.g., Eid-specialising boutiques in Ramadan)
- Corporate gifting sellers section (separate component, same architecture)
- International seller cards with country flag (future)

#### Design risk

**LOW.** This section rarely causes homepage redesign problems. Risk: seller cards
with inconsistent logo quality can degrade perceived premium feel. Mitigation: enforce
a `min-height` placeholder for missing logos; use seller initials as fallback.

#### Audit priority

**Priority 5.** Trust-building; indirectly supports all conversions but not the primary
revenue driver of product rails.

### Section 6 — Occasion Discovery

**Component owner:** Not yet implemented. Planned as `OccasionGrid.jsx` or similar.
**CSS owner:** Section-specific scoped class prefix `occasion-` or CSS module
**Design reference:** D1.6 (pending)
**Current audit status:** `pending`

#### Section job

Give users a gifting route based on the occasion they have in mind. Bridge the gap
between "I want to give a gift" and "I want to give a birthday gift for my mother."
Occasions are the most common real-world purchase trigger.

#### User question it answers

> "I'm buying this for a specific occasion — where do I go?"

#### Occasions

| Occasion | Route |
|---|---|
| Birthday | `goToShop` with occasion filter (future) or curated collection |
| Anniversary | As above |
| Eid / Ramadan | Seasonal collection or occasion filter |
| Thank You | As above |
| Congratulations | As above |
| Corporate gifting | Dedicated flow (future) |

#### Primary CTA

Per occasion card: **Shop [occasion]** — routes to a filtered shop or collection page.

#### Secondary CTA

None at section level. Each card is self-contained.

#### Data dependency

**LOW to MEDIUM.** Occasion cards may be static (hardcoded label + image + route) or
API-driven (occasion collections from admin). Start static, move to API when collections
are live.

#### Future expansion points

- Seasonal suppression: hide or reorder occasions based on the current calendar
  (e.g., surface Eid cards prominently in Ramadan)
- Corporate gifting as a full sub-section with its own CTA and dedicated landing page
- Occasion-based product recommendations (API, future)
- User-personalised occasion reminders (account feature, future)

#### Design risk

**MEDIUM.** Risk of becoming a navigation mega-menu. Hard constraint: **maximum six
occasion cards visible on one row or two rows.** Additional occasions must go behind
a "More occasions" expand or a dedicated occasions page.

#### Audit priority

**Priority 6.** High strategic value; currently not implemented. Unblocks corporate
and seasonal campaign revenue.

### Section 7 — Editorial / Journal Preview

**Component owner:** Not yet implemented. Planned as `JournalPreview.jsx` or similar.
**CSS owner:** Section-specific scoped class prefix `journal-` or CSS module
**Design reference:** D1.7 (pending)
**Current audit status:** `pending`

#### Section job

SEO, brand authority, and gifting inspiration. Show that Tuti is a thoughtful brand
with editorial voice, not just a transactional marketplace. Gives returning visitors a
reason to re-engage. Supports organic search traffic for gifting-intent queries.

#### User question it answers

> "Does this brand know what it's talking about? Can I trust their taste?"

#### Content

| Element | Description |
|---|---|
| Gift guides | Curated "best perfumes for Eid" type articles |
| Perfume pairing stories | Scent + occasion + recipient narrative pieces |
| Dessert pairing stories | Cake + gift occasion editorial pieces |
| Section CTA | **Read the journal** — calls `goToJournal` |

#### Primary CTA

**Read the journal** at section level or per-article card CTA.

#### Secondary CTA

None required.

#### Data dependency

**MEDIUM.** Journal articles come from a CMS or static content layer. Until the journal
is populated, this section renders `null` or a single placeholder card. Do not render
empty section chrome.

#### Future expansion points

- Editorial collections linked directly to occasion discovery (Section 6)
- Seasonal editorial campaigns (Eid gift guide, Valentine's picks, etc.)
- Author attribution and estimated reading time
- SEO: pre-render or SSG journal preview cards for crawlability

#### Design risk

**LOW.** This section is below the primary conversion fold. Risk: editorial cards with
poor imagery can lower the perceived quality of the entire page. Mitigation: enforce
a minimum card image quality standard or use typography-first fallback cards.

#### Audit priority

**Priority 7.** SEO and brand value; not on the primary conversion path. Implement
after all conversion sections are stable.

### Section 8 — Trust / Service Promise

**Component owner:** `TrustClosing` (currently in `HomePage.jsx`); planned migration to
standalone `apps/web/src/features/homepage/TrustSection.jsx`
**CSS owner:** `trust-closing-*` class system in `storefront.css` (existing)
**Design reference:** D1.8 (pending)
**Current audit status:** `pending`

#### Section job

Reduce purchase anxiety at the point just before the final CTA. Reinforce that Tuti
is trustworthy, reliable, and premium. Address the four most common objections: seller
quality, packaging quality, checkout security, and delivery reliability.

#### User question it answers

> "Is it safe to buy here? Will it actually arrive well?"

#### Trust signals

| Signal | Copy direction |
|---|---|
| Curated sellers | Every boutique passes a quality review before going live |
| Premium packaging | Gifts are assembled and boxed with care |
| Secure checkout | COD-first; no payment surprises |
| Delivery promise | Local UAE delivery with tracking |

#### Primary CTA

None. This section is reassurance, not conversion. The CTA lives in Section 9.

#### Secondary CTA

None.

#### Data dependency

Static. All trust signals are editorial copy.

#### Future expansion points

- Verified seller count (dynamic: "120+ verified sellers")
- Delivery speed promise (API: real delivery time estimate by emirate)
- Customer review aggregate (e.g., "4.8/5 from 2,400 orders")
- Trust badge imagery (e.g., secure payment icons, COD logo)

#### Design risk

**LOW.** Risk of being too verbose and creating a second homepage — put trust signals
in a compact, scannable format (icon + strong label + one-line descriptor). Hard
constraint: **maximum four trust signals. No paragraphs.**

#### Audit priority

**Priority 8.** Important for conversion completion; low design risk; stable once
implemented.

### Section 9 — Final CTA / Closing

**Component owner:** To be implemented as `HomepageClosing.jsx` or inline in `HomePage.jsx`
**CSS owner:** Section-specific, minimal
**Design reference:** D1.9 (pending)
**Current audit status:** `pending`

#### Section job

Final conversion push. The user has seen the brand story, browsed products, read trust
signals. Give them one last clean invitation to act. This is the most intentional CTA
on the page — it converts visitors who scrolled the whole way through.

#### User question it answers

> "OK, I'm ready. What do I do now?"

#### CTAs

| CTA | Action |
|---|---|
| **Build your gift** (primary) | `goToBuildBox` |
| **Explore gift sets** (secondary) | `goToShop("gift_box")` |

#### Primary CTA

**Build your gift** — large, prominent, primary action style.

#### Secondary CTA

**Explore gift sets** — ghost/secondary style.

#### Data dependency

Static. No API calls.

#### Future expansion points

- Seasonal CTA variant ("Build your Eid gift" in Ramadan)
- Subscription teaser ("Be the first to know — join the list")
- Referral / share prompt for repeat visitors

#### Design risk

**LOW.** The closing CTA is a well-understood pattern. Risk: making it so minimal it
disappears, or so bold it feels like a hard sell. Match the register of the hero invite —
confident and warm, not pressuring.

#### Audit priority

**Priority 9.** Lowest design risk; highest completion-rate leverage for long-scroll
visitors.

## Implementation Rules

### One section = one component

Each section should have a single owner component file in
`apps/web/src/features/homepage/` or a dedicated subfolder.

```
apps/web/src/features/
  immersive/          ← Section 1 (Hero)
    ImmersiveStory.jsx
    immersive.css
    useImmersiveStory.js
  homepage/           ← Sections 2–9
    PathSelector.jsx
    GiftBuilderPreview.jsx
    AdaptiveProductEdit.jsx   ← Section 4 (already exists)
    AdaptiveBoutique.jsx      ← Section 5 (already exists)
    OccasionGrid.jsx          ← Section 6 (future)
    JournalPreview.jsx        ← Section 7 (future)
    TrustSection.jsx          ← Section 8 (migrate from inline)
    HomepageClosing.jsx       ← Section 9 (future)
    homepage.css              ← shared homepage utility styles only
```

### Separation of concerns

| Rule | Rationale |
|---|---|
| Do not put hero logic inside product rails | Hero and product discovery have different data, timing, and animation concerns |
| Do not mix PathSelector with GiftBuilderPreview | Path selection is navigation; gift builder preview is education |
| Do not put API calls inside the hero | The hero is static; mixing async data creates unnecessary loading states above the fold |
| Do not use global CSS patches for section-specific styles | Global patches break isolation and make audits unreliable |

### CSS scoping

- Each section component uses a unique class prefix (e.g., `is-` for immersive, `path-`
  for PathSelector, `gift-preview-` for GiftBuilderPreview).
- Do not add section-specific CSS to `storefront.css` unless the style is genuinely
  global (e.g., a shared button variant used across the entire app).
- Do not add section-specific CSS to `homepage.css` unless it is a shared utility used
  by more than two homepage sections.

### Independent auditability

Every section listed in this document must have its own D0.2 audit entry before it
may ship to production. An audit entry covers:

- Mobile-first visual pass (375px)
- Desktop visual pass (1280px)
- All 14 D0.1 scoring dimensions
- State audit (default, hover, focus, active, error, empty, loading, reduced-motion)
- Accessibility spot-check
- Human taste review
- Pass/fail decision

## BMAD Workflow — Homepage Section Change

Apply this workflow to every homepage section change, in order. Do not skip steps.

```
1. AUDIT (read-only)
   └── Read current section files
   └── Run D0.1 checklist against current implementation
   └── Record findings in D0.2 (new entry or update)
   └── Classify: PASS / CONDITIONAL / FAIL / NEEDS-RE-AUDIT

2. PLAN
   └── List specific fixes as a numbered Fix Batch (e.g., Fix Batch A)
   └── Mark each fix: hard fail / soft fail / design improvement
   └── Estimate blast radius: does this fix touch other sections?
   └── Get explicit approval before implementation

3. IMPLEMENT
   └── Touch only the approved files for this section
   └── No scope creep into other sections
   └── No global CSS unless explicitly approved

4. VERIFY
   └── git diff --check (no whitespace errors)
   └── git status --short (only expected files changed)
   └── Grep for deleted class names (confirm no orphaned CSS)
   └── Brace/import balance check on JSX

5. RE-AUDIT
   └── Re-run D0.1 against changed files
   └── Update D0.2 entry with new scores
   └── Confirm PASS or CONDITIONAL

6. COMMIT
   └── One commit per approved Fix Batch
   └── Commit message references D0.2 entry and Fix Batch ID

7. NEXT SECTION
   └── Return to step 1 for the next priority section
```
